RunTrack

Un coureur démarre, ses amis sont prévenus, ils suivent sa position en direct, et la course est historisée à l'arrivée.

Neuf modules fonctionnels, 810 tests, 94 % de couverture ligne. Le back-end est complet : les treize lots du cahier des charges sont livrés, et chaque écart assumé est expliqué à l'endroit du code où la question se pose.

Cette page décrit ce qui n'est pas lisible dans le code : pourquoi le découpage est celui-là, ce qui traverse plusieurs modules, et les décisions dont on ne devine pas la raison en lisant une classe isolément.

Le découpage

Le premier niveau est fonctionnel, jamais technique. L'architecture hexagonale s'applique à l'intérieur de chaque module, pas au-dessus.

auth ─────────┐
social ───────┼──▶ user
course ───────┘
sharing ──────┐
engagement ───┼──▶ course
              │
notification ─┴──▶ user, social, course, engagement   (personne n'en dépend)
feed ────────────▶ user, social, course, engagement   (personne n'en dépend)

Le graphe est déclaré à deux endroits, volontairement : dans les pom.xml — Maven refuse un cycle — et dans les @ApplicationModule(allowedDependencies = …), car Modulith interdit en plus d'atteindre les paquets imbriqués du voisin, ce que le classpath autoriserait.

Chaque module a la même forme, avec le vocabulaire des APIs Lark :

course/
├── CourseApi.java        seul point d'entrée pour les autres modules
├── event/                événements publiés — contrat inter-modules
├── usecases/
│   ├── model/            Java pur : ni Spring, ni Jakarta, ni Jackson, ni JPA
│   ├── service/          cas d'usage
│   └── port/             ports sortants
└── infrastructure/
    ├── endpoint/ dto/    REST
    ├── repository/       implémentations des ports
    └── cache/ realtime/

Deux écarts assumés à ce vocabulaire

Les ports vivent dans usecases/port/, pas dans infrastructure/repository/. La dépendance va vers le centre, et une règle ArchUnit le vérifie à chaque build : adopter l'autre position échangerait une garantie vérifiée contre un nom de dossier.

Un seul @ControllerAdvice, global. Le scoper par assignableTypes laisse les endpoints d'une seconde version d'API sans mapping — leurs exceptions remontent alors en 500 au lieu de 401 ou 403. Ce piège est documenté dans un service réel ; l'importer serait un choix, pas un oubli.

Le direct — de la montre à l'écran d'un spectateur

Le point difficile n'est pas d'émettre un événement, c'est qu'un spectateur connecté à l'instance B voie une course dont les points arrivent sur l'instance A.

  téléphone du coureur                     spectateurs
         │                                  ▲        ▲
         │ POST /activities/{id}/points     │ SSE    │ SSE
         ▼                                  │        │
   ┌───────────────┐                 ┌──────┴──┐  ┌──┴──────┐
   │  instance A   │                 │  inst.A │  │  inst.B │
   │ PointIngestion│                 └────┬────┘  └────┬────┘
   │   ├ filtre    │                      │ registre   │ registre
   │   ├ dédup     │                      │ d'émetteurs│
   │   ├ accumule  │                      ▲            ▲
   │   └ COMMIT ───┼──────────┐           │  XREAD     │  XREAD
   └───────────────┘          │           └────────────┴──────┐
                              ▼                                │
                   ┌──────────────────────────────────┐        │
                   │ Dragonfly Stream                 │────────┘
                   │ live:activity:{id}:events        │
                   │ MAXLEN borné · id: = Last-Event-ID
                   └──────────────────────────────────┘

Trois enchaînements de ce schéma ne sont pas interchangeables :

  1. la publication attend le commit. Annoncer une position avant, c'est l'annoncer alors qu'un conflit optimiste peut encore l'effacer — et ce conflit est ordinaire, pas exceptionnel ;
  2. on s'abonne au flux avant de lire l'instantané, et l'instantané est inséré en tête de la file du spectateur. L'inverse perdrait les événements survenus pendant la lecture en base, sans que personne ne s'en aperçoive ;
  3. une instance ne suit une course que tant qu'elle a un spectateur pour elle. C'est ce qui borne le nombre de connexions ouvertes.

Un piège coûteux, trouvé en test d'intégration. ReadOffset.latest() fait repartir Spring de « maintenant » à chaque lecture : tout ce qui s'écrit entre deux XREAD tombe dans le vide. Un lot de quatre points n'en faisait parvenir qu'un, sans la moindre erreur.

Les abonnements partent désormais d'un identifiant d'entrée concret. Aucun test unitaire n'aurait pu l'attraper.

Le registre apporte — et dispense donc d'écrire — l'exécution après commit, en asynchrone, l'événement persisté avant traitement et complété après, et le rejeu au redémarrage. Restent à notre charge : le recul exponentiel entre deux reprises, l'arrêt après cinq échecs, et le fait qu'aucun appel à Firebase ne se trouve dans une transaction métier.

L'idempotence tient dans un identifiant

Un rejeu ne doit pas notifier deux fois. L'identifiant d'une notification est donc déduit de ce qui l'a provoquée — nature, destinataire, sujet, et l'instant de l'événement — puis l'insertion ignore les conflits. Se réabonner à quelqu'un notifie quand même : c'est un second événement, pas un rejeu.

Le fil de corrélation traverse les fils d'exécution

Un ScopedValue ne franchit pas un changement de fil. L'identifiant de corrélation voyage donc dans le champ correlationId de chaque événement, et la portée est rouverte à l'entrée de chacun des dix-sept écouteurs. Sans ce geste, les journaux ne seraient corrélés que sur le chemin HTTP — et on ne s'en apercevrait qu'en cherchant, en production, pourquoi une notification est partie.

Ce que le cahier des charges appelait des pièges

SujetLa décision, et pourquoi
Fan-out du fil À la lecture. Une ligne par destinataire ferait des dizaines de milliers d'insertions au démarrage d'une course d'un compte très suivi.
Décision canView Jamais cachée. Cardinalité N×M, invalidation impossible à cibler. On cache les faits, on recompose la décision en mémoire : c'est gratuit et exact.
Blocages Jamais cachés. Une valeur périmée de cinq minutes laisserait quelqu'un voir ce qu'il ne doit plus voir. Un cache qui peut rouvrir une porte n'en est pas un.
Lien de partage Le jeton est stocké haché : une fuite de la base ne doit pas ouvrir les courses partagées. SHA-256 et non Argon2 — un secret de 256 bits tiré au sort n'a pas de dictionnaire, et le hachage lent coûterait à chaque ouverture.
Quota de connexion Deux axes. Par IP contre le balayage de mille comptes, par compte contre le forçage d'un mot de passe en changeant d'adresse. Le quota par IP est vingt fois plus large : une adresse est partagée, un compte ne l'est pas.
Points bruts Purgés 90 jours après historisation, et seulement pour ce qui a été archivé. Conséquence assumée : l'export GPX n'est possible que dans cette fenêtre.

Démarrer en local

docker compose up -d                  # Postgres + PostGIS, Dragonfly
export JAVA_HOME=$(/usr/libexec/java_home -v 25)
mvn verify                            # compile, tests, seuil de couverture
mvn -pl runtrack-app spring-boot:run  # profil `local` par défaut

Puis http://localhost:8080/swagger-ui.html. Le fichier docs/api/runtrack.http parcourt l'API de bout en bout — créer un compte, courir, partager, commenter — et s'ouvre dans IntelliJ comme dans VS Code.

Deux choses font échouer un premier lancement, et leurs messages ne le disent pas : le build exige un JDK 25, et les tests d'intégration démarrent des conteneurs — sans Docker en marche, une cinquantaine d'entre eux échouent d'un bloc sur un message qui ressemble à une panne de code.

Ce que le build vérifie

  • ApplicationModules.verify() — frontières, cycles, interfaces nommées ;
  • onze règles ArchUnit : domaine sans framework, sens des dépendances, JPA et cache confinés à l'infrastructure, aucun reactor.*, pas de Lombok, injection par constructeur, aucun Instant.now() en dur ;
  • 80 % de couverture ligne et branche, sur l'union unitaires + intégration, haltOnFailure ;
  • la description OpenAPI, générée et vérifiée : une documentation générée échoue en silence, et un /v3/api-docs qui répond 200 avec zéro chemin est le pire des deux mondes.

Documentation générée à chaque déploiement depuis le dépôt. La référence de l'API est produite par le build, pas écrite à la main.
